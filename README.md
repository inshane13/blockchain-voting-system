# Blockchain-Based Voting System

A decentralized voting dApp on Ethereum using a two-phase **commit-reveal** scheme. Solidity smart contracts (Hardhat), a Next.js + MetaMask frontend, and an Express + SQLite backend used only as an off-chain audit log.

## Features

- **Commit-Reveal Voting**: Voters commit a hash during the commit phase and reveal the plaintext during the reveal phase, preventing vote-buying and front-running.
- **Voter Registration**: Admin-controlled eligibility via `VoterRegistry`.
- **On-Chain Results**: `getWinner()` / `getTotalVotes()` compute the result directly on-chain (with tie detection).
- **Modern Frontend**: Next.js + ethers v6 + MetaMask, with salt persistence across page reloads.
- **Off-Chain Event Log**: Express + SQLite stores `VoteCommitted` / `VoteRevealed` events for auditing (non-authoritative).
- **Comprehensive Tests**: Hardhat/Chai suite covering collisions, phase boundaries, invalid reveals, and winner logic.

> There are **no ZK-SNARKs**. The package description previously mentioned them in error; that has been corrected.

## Architecture

### Smart Contracts
- **`VoterRegistry.sol`**: Owner-managed eligibility whitelist. Authoritative on-chain source of truth for `isEligible(address)`.
- **`Voting.sol`**: Single-election commit-reveal logic, per-voter commitments, deadlines, tally, and winner calculation.

### Frontend
- **Next.js** single page (`frontend/pages/index.js`)
- **ethers v6** + `@metamask/detect-provider`
- Reads eligibility directly from `VoterRegistry` (the chain is the source of truth)

### Backend
- **Express.js** REST API (`backend/server.js`)
- **SQLite** (`better-sqlite3`) persistence for the off-chain event log
- Eligibility endpoint is explicitly **non-authoritative**

## Setup Instructions

### Prerequisites
- Node.js (v18 or higher)
- npm
- MetaMask browser extension

### 1. Install Dependencies

```bash
npm install
cd backend && npm install
cd ../frontend && npm install
```

### 2. Environment Configuration

```bash
cp .env.example .env
cp frontend/.env.example frontend/.env.local
```

Fill in real values for `SEPOLIA_URL` and `PRIVATE_KEY` in `.env`. The frontend
`.env.local` is auto-generated by the deploy script.

### 3. Compile Smart Contracts

```bash
npx hardhat compile
```

### 4. Run Tests

```bash
npx hardhat test
```

### 5. Deploy Contracts

```bash
# Local
npx hardhat node
npx hardhat run scripts/deploy.js --network localhost

# Testnet (configure .env first)
npx hardhat run scripts/deploy.js --network sepolia
```

`deploy.js` writes `deployments.json` and regenerates `frontend/.env.local`.

### 6. Register Voters

```bash
npx hardhat run scripts/registerVoter.js --network sepolia <VOTER_ADDRESS>
```

Reads the registry address from `deployments.json`; defaults to the deployer if no address is given.

### 7. Start the Applications

```bash
# Backend (defaults to :5000)
cd backend && npm run dev

# Frontend
cd frontend && npm run dev
```

## Usage

### For Voters
1. **Connect Wallet** via MetaMask.
2. **Check Eligibility** (read from `VoterRegistry.isEligible`).
3. **Commit Phase**: select a candidate, enter a secret salt, and commit. The salt string is saved in the browser for later.
4. **Reveal Phase**: reveal using the same salt. On success the stored salt is cleared.
5. **View Results**: live tallies plus the on-chain leader/tie.

### For Administrators
1. Deploy contracts (`scripts/deploy.js`).
2. Register voters (`scripts/registerVoter.js`).
3. Monitor progress and results.

## Smart Contract Details

### Phase Timing

Let `T0` be the deployment timestamp, `Ct` the commit duration, and `Rt` the reveal duration:

- Commit deadline: `C = T0 + Ct`
- Reveal deadline: `R = T0 + Ct + Rt`

- Commit valid when `block.timestamp < C`
- Reveal valid when `C <= block.timestamp < R` (the reveal phase includes the exact `C` boundary, closing the former 1-second dead zone)

### Commitment Scheme

The frontend computes:

```
salt = keccak256(bytes(userString))
H    = keccak256(abi.encode(candidateIndex, salt))
```

- **Hiding**: `candidateIndex` is not recoverable from `H` during the commit phase.
- **Binding**: changing the choice requires changing `H`.
- `abi.encode` (not `abi.encodePacked`) avoids hash-collision padding bugs.

### Storage & Griefing Fix

Commitments are stored **per voter** (`mapping(address => bytes32)`), not in a
global hash set. Two voters choosing the same `(candidateIndex, salt)` no longer
collide: each reveal checks `commits[msg.sender]` independently.

### Tally & Winner

- On each valid reveal: `votes[idx] += 1` (O(1)).
- `getTotalVotes()`: sum of all candidate tallies.
- `getWinner()`: O(N) scan returning `(winnerIdx, winnerVotes, tied)`. `tied` is true when two or more candidates share the highest count greater than zero.

## Security Notes

- **Eligibility is checked on-chain** at commit time via `VoterRegistry.isEligible`. The backend endpoint is non-authoritative and must never be trusted for eligibility.
- **One vote per address** enforced by `hasCommitted` / `hasVoted`.
- **No secrets in source control**: use `.env` (gitignored). Rotate any credentials that may have been committed previously.
- **Single-election contract**: deploy a new `Voting` contract per election.
- No on-chain quorum or vote weighting is implemented.
